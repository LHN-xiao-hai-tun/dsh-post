# 02 · 命名与落点

这一篇是**格式契约**。想改格式，先想清楚会不会把老数据读坏。

---

## 一、目录长什么样

每台设备一个工作区，工作区里固定这几样（名字都在 `bridge.toml` 里配，下面只是默认写法）：

```
<workspace>/
├─ 收件箱/                    ← [device.X].inbox       别人投给你的件
│  ├─ pc/ …                   ← [receive].layout="subdir" 时按收件方分格
│  ├─ tablet/
│  ├─ .received.json          ← 收件归位台账 {文件名: md5}
│  └─ 知会_给电脑_主题_20261107.md
├─ 发件箱/                    ← [device.X].outbox      你要发出去的件（放这里就会被投）
│  ├─ 已发/                   ← [device.X].sent_dir    投成功后 copy2 的留档（默认 outbox/已发）
│  ├─ .posted.json            ← 投递台账 {文件名: md5}
│  ├─ .post.lock              ← 单实例锁
│  └─ post.log                ← 投递日志 `[YYYY-MM-DD HH:MM:SS] 消息`
├─ 聊天室/                    ← [hub].path 的所在目录（默认在中心那台）
│  ├─ hub.jsonl               ← 中心：所有设备追加的同一个文件
│  ├─ hub.jsonl.meta          ← 归档闸 {first_seq, line_offset, archived_at, archived_rows}
│  ├─ hub.bad.jsonl           ← 坏行原文 {line_no, at, raw_b64}
│  ├─ hub.jsonl_旧.jsonl      ← 归档挪出的老行
│  └─ .chat.beat              ← 心跳：epoch 浮点串
└─ .dsh/state/                ← [general].state_dir    每台自己的私有状态
   ├─ .chat_cursor_<设备key>  ← 聊天游标
   ├─ dsh_bridge_loop.pid
   ├─ dsh_bridge_loop.json    ← 守护状态
   └─ dsh_bridge_loop.lock
```

三件**故意**没做的事：

1. **⛔ 不递归扫发件箱。** `已发/` 在发件箱里面，递归会把留档件当待发重投一遍。
2. **⛔ 不把游标放中心目录。** 游标是每台的私有进度，放共享目录会让三台互相踩。
3. **⛔ 不改工作区里已有的任何文件。** 只往里加。

## 二、信件文件名

```
性质_发给谁_主题_日期.md
```

正则（代码里的唯一权威，`bridge/post.py` 的 `FNAME_RE`）：

```
^(?P<act>[^_]+)_(?P<to>[^_]+)_(?P<subject>.+)_(?P<date>\d{8}|\d{4}-\d{2}-\d{2})\.md$
```

| 段 | 要求 | 例子 |
|---|---|---|
| 性质 `act` | 必须是 `[naming].act_kinds` 里的一个 | `信` `回话` `同步` `知会` |
| 收件方 `to` | 必须能在 `[recipients]` 里查到（可带 `发给`/`给`/`回` 前缀） | `给大家` `给平板` `回手机` |
| 主题 `subject` | 除 `_` 外随便写（**可以有空格、中文、标点**） | `跨设备打包验收` |
| 日期 `date` | `20261107` 或 `2026-11-07`，末尾统一 `.md` | `20261107` |

```
✅ 知会_给平板_跨设备打包验收_20261107.md
✅ 信_给大家_周五的结论_2026-11-07.md
✅ 回话_回手机_上次那个问题_20261107.md
❌ 通知_给平板_主题_20261107.md      ← 性质不在表里（bad-act）
❌ 知会_给丙机_主题_20261107.md      ← 收件方查不到（bad-target）
❌ 知会_平板_20261107.md             ← 段数不对（bad-fields）
```

### 为什么三种错误要分开报

| 原因 | 修法 | 一句话 |
|---|---|---|
| `bad-fields` | 整份改名 | 段数/日期都不对，模板都没对上 |
| `bad-act` | 改**一个词** | 第一段不在 `act_kinds` 里 |
| `bad-target` | 改**一个词** | 第二段在 `[recipients]` 里查不到 |

混成一句「名字不规范」，等于让人自己去找哪里不规范。

> ⚠️ **顺序是契约**：`validate_name_all()` 固定先报 `bad-fields`，再 `bad-target`，最后 `bad-act`。
> `--status` 和 `--once` 靠「第一个原因」分类汇报；顺序一反，双错的件会落进「待发」，
> 下一轮又必被拦，日志里就变成「报待发 1 个」的死循环观感。

### 老件怎么办

`[naming].enforce_since = "20261105"` 表示：**文件名里的日期**早于这天的，
不按新规矩校验（老件不该因为规矩变了突然变成「不合规」）。

⚠️ 判据是**文件名里的日期**，不是文件修改时间：
`cp -p`、解包、归档搬运都会保留旧时间戳，拿 mtime 判新旧等于拿一个会被搬运改变的东西
去证明「它没变过」。

## 三、`hub.jsonl` 的行格式（⛔ 不可改）

```json
{"seq": 1, "from": "phone", "at": "2026-11-05 18:12:06", "text": "..."}
{"seq": 2, "from": "tablet", "at": "2026-11-05 18:15:31", "text": "...", "via": "笔记本"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq` | int | 消息序号，从 1 起，**只增不减**。归档后继续往上加，⛔ 不重排 |
| `from` | str | 谁说的（设备 key，见 `[device.*]`；也可以是你自己起的名字） |
| `at` | str | `YYYY-MM-DD HH:MM:SS` 本地时间 |
| `text` | str | 正文。长度上限 `[naming].max_text_chars` |
| `via` | str? | **可选**。和 `from` 不同时才写（「经谁转发」） |

**这个格式是对外契约**：既有的 700+ 条消息就是它，新包必须原样能读。
`via` 是可选字段、**不在必填 schema 里** —— 所以校验只查前四个的类型。

### seq 和物理行号是两件事

- `seq` 答：**我说到第几条**（给人看、算偏移）
- 行号答：**我读到文件第几行**（去重只认它）

为什么非要两个：只追加的文件里行号天然唯一，而 seq 是「谁先读到谁分配」，
并发写会**撞号**。撞号之后如果拿 seq 去比「新不新」，那两条就都读不到，
`--status` 还报「差 0 条」—— 静默丢消息，最难查的那种。

游标文件（`.dsh/state/.chat_cursor_<设备key>`）两个格式都认：

```
7                                  ← 老格式：一个整数，按 seq 比
{"seq": 7, "line": 42}             ← 新格式：优先按 line 比
```

读到老格式会自动按老规矩走，下一次写游标就升级成新格式。**不需要手工迁移。**

## 四、坏行与归档

**坏行**：非空、但解不出 `seq`（int）和 `text`（str）的行。
空行不算坏行（它只是占号），`from`/`at` 缺失只降级显示成 `?`（历史行可能是别家工具写的）。

坏行**跳过不崩**，原文按 base64 记进 `hub.bad.jsonl`：

```json
{"line_no": 43, "at": "2026-11-05 19:00:12", "raw_b64": "eyJzZXEiOiA0Mywg..."}
```

按 `line_no` 去重，同一行不会被记两遍。

**归档**（`python -m bridge.chat --archive`）：把老行挪进 `hub.jsonl_旧.jsonl`，
并在 `hub.jsonl.meta` 里推进两个数：

```json
{"first_seq": 5201, "line_offset": 5200, "archived_at": "...", "archived_rows": 5200}
```

- `first_seq`：现在文件里第一条的 seq（用来判断游标是不是落进了已归档区间）
- `line_offset`：**已经挪走多少物理行**。读的时候行号按它平移，
  所以游标里存的绝对行号在归档前后指向同一条消息 —— 归档不会让客户端重读或漏读。

⚠️ 归档只能在**中心所在的那台机器**上跑：它是在重写那个共享文件，
别台正在追加时切一刀会丢数据。远端中心上跑会被明确拒绝。

## 五、编码

- 所有文本文件一律 **UTF-8 无 BOM**（`bridge.toml` 允许带 BOM，读的时候用 `utf-8-sig`）。
- 信件正文按**字节**原样搬运，⛔ 不做换行符转换、不做编码转换。
- 校验 md5 就是为了证明这一点：投过去和原件**字节一致**才算投成功。
- Windows 控制台默认代码页常常是 936/GBK，本包启动时把 stdout/stderr 切到 UTF-8
  并带 `errors="replace"` —— 一个只负责打印的字符不该能让投递失败。
- `.ps1` 必须带 UTF-8 BOM：Windows PowerShell 5.1 读无 BOM 的 UTF-8 脚本会按 ANSI 解，
  中文全变乱码，而且常常是「语法错误」而不是「乱码」的报错形式。
