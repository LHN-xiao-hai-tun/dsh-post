# 04 · 安卓 / proot 环境的额外坑

> 用途：`dsh-post` 装到别人机器上以后，**卡住了先查这里**。
> 本篇只写**我们真踩到过**的坑，每条带「症状 → 原因 → 处理」。
> 面向通用用户，路径一律用占位符 `{{WORKSPACE}}` / `{{HOME}}`；**⛔ 不要写我们三台的真路径、真 IP、真主机名**（推公开仓前要过脱敏扫描闸）。

> 这份只讲 **Android + proot** 特有的问题。通用的「不投 / 重复投 / 看不到消息」看 `03_故障排查.md`。

## 0. 先跑体检，再看别处

```bash
bridge doctor
```

一条命令输出：预期 hostname 是否对得上、sshd 端口在不在、别名能不能连、单实例锁有没有被占。
**先跑 doctor 再读下面的章节** —— 大部分"装完不工作"是配置问题，不是 bug。

## 1. `bridge receive` 不收件

### 1.1 三处收件口一个都没动静
**症状**：守护在跑，日志干净，就是没有件。

**排查顺序**（⛔ 别跳步）：
1. 落点目录存在吗？`ls -d {{INBOX1}} {{INBOX2}} {{INBOX3}}` —— **proot 里手工建目录常常会失败或建到别处**。
2. 挂载点在吗？`mount | grep -E 'sdcard|emulated'` —— 手机/平板上内部存储是 bind mount，**没挂上时目录看起来存在但是空的**。
3. 落点里是不是有权限问题？`touch {{INBOX1}}/.probe && rm {{INBOX1}}/.probe`。
4. **inotify 在这台机器上到底能不能用** —— 有的 proot 内核不支持。`inotifywait` 不一定装了，用我们的自检：
   ```python
   import ctypes
   libc = ctypes.CDLL("libc.so.6")
   fd = libc.inotify_init()
   print("fd =", fd)          # fd < 0 ⇒ 这台机器不支持 inotify
   wd = libc.inotify_add_watch(fd, b"/path/to/inbox", 0x00000100)  # IN_CREATE
   print("wd =", wd)         # wd < 0 ⇒ 这条路径 watch 不了
   ```
   **wd < 0 时不要重试** —— 守护会退回 10 秒轮询，**功能是好的，只是慢**。
5. 判重是不是把件误杀了？看 `.md5` 台账里有没有这条件名。

### 1.2 收件了但"看不到"
**症状**：文件在落点里，但界面/通知没有。

**原因**：发现层和上层是两件事。
- **发现层** —— ⚠️ **通用包这一版没有**。`receive.py` 只做**按命令归位**（把收件箱里的信按收件方分格 + md5 判重），**没有 watcher、没有 inotify、没有三落点扫描**。你不在的时候进来的信，就静静躺在收件箱里，等你跑一次 `bridge.receive --once`。
- **想要「一进来就自动处理」**：得你自己在外面挂一个 watcher —— proot 上就是本章 §1.1 那套（inotify 可用就 inotify，不可用就 10 秒轮询），上面那些落点是你自己配的，不是包给你的。
- **上层**（DSH 特有）：未读卡片、系统通知、投 `.dsh/share_queue/*.json` 唤起会话 —— **⛔ 这层不在通用包里**（DSH 私有协议，搬出去没有接收方）。

**处理**：装通用包的人拿不到"会话被唤起"，这是设计如此，不是 bug。想要这层得自己接 DSH 插件。

### 1.3 漏收、隔很久才收到
**症状**：件在，但延迟 10 秒到几分钟。

**原因**：inotify 不可用，退回了 10 秒轮询兜底。**正常行为**。

**处理**：想更快就确认 inotify 可用（§1.1 第 4 步）。

## 2. 文件名和落点不合法 → **静默丢掉**（最容易踩）

**症状**：件"发出去了"，对面说没收到，日志里也没报错。

**原因**：文件名必须符合 `^(信|回话|同步|知会)_(收件方)_(主题)_(日期).md` 这类约定，日期是 `YYYYMMDD` 或 `YYYY-MM-DD`。**不合规的名字不会被投出去，也不会报错** —— 这是设计（避免脏名进 hub），但对新手是坑。

**处理**：
```bash
bridge lint          # 校验待发件的名字与落点
```
`validate_name` 就是从投递逻辑里抽出来的同一套判据。

**还有两条硬规矩**：
- **发件文件名必须带目标**（`回话N_给电脑_日期.md`），不带目标会误投到别的设备的收件箱。
- **收件方**：电脑只收「给电脑」的件；平板和手机收「给平板」「给手机」的件；「给大家」的件三方都收。

## 3. md5 判重把件误杀了

**症状**：同一份件反复发，对面只收到一次。

**原因**：判重按**文件内容的 md5**。同一份内容改了名字也是重复 —— 这是故意的（防"改个名再发一遍"灌水）。

**处理**：要重发一份内容不同的件就改内容；确实要原样重发，让对方先清台账。

## 4. 单实例锁：第二个实例永远起不来

**症状**：`bridge receive` 起第二次，日志报锁被占，立刻退出。

**原因**：防双开。**但这把锁有个坑** —— 某些实现里锁绑在「打开的文件描述」上，同一个进程下一轮循环会把自己锁住（**每轮都排斥自己**）。所以「第二个实例被拒」这条测试**不够**，必须再加一条「锁真的放行新实例」。

**处理**：
```bash
cat {{WORKSPACE}}/.bridge/daemon.lock   # 看里面记的 pid
kill -0 <pid> && echo 还活着 || echo 死了，可以清掉
```
**只删锁文件，不要删正在跑的实例。**

## 5. sshd 起不来 / 连不上

### 5.1 装完 sshd 一重启就没了
**症状**：整机重启后 ssh 连不上。

**原因**：**在某些 proot 镜像里，整机重启会把 `openssh-server` 整个包装丢掉**（实测 `dpkg -l` 都查不到）。这不是"服务没起"，是"包没了"。

**处理**：`install.sh` 里必须自带装包那一步，⛔ 不能假设系统已装：
```bash
apt-get update && apt-get install -y openssh-server
```

### 5.2 包在，但 sshd 启动即退
**症状**：`/usr/sbin/sshd` 存在，但连不上；直接跑它没报错也没进程。

**原因**：**proot 里 `/run` 是 tmpfs，重启就没了**，`sshd` 缺 `/run/sshd` 这个 privsep 目录会**直接退出**（不写日志）。

**处理**：
```bash
mkdir -p /run/sshd
/usr/sbin/sshd -e     # -e 让错误打到 stderr，看得见
```

### 5.3 "起了但连不上"——最难的一类
**症状**：22 端口在听，`ssh` 却报 connection refused 或连到别的机器。

**原因**：**你以为连的是 A，实际连的是 B**（内网另一台同 IP / DHCP 变了 / alias 指到了另一台）。

**处理**：`bridge doctor` 的 hostname 断言就是治这个的 —— 连上后先 `hostname` 对一遍，别只看端口通不通。

### 5.4 别拿 `ps` 判存活
**症状**：想用 `ps -ef | grep xxx` 看守护还在不在。

**原因**：**在 proot 里 `ps -ef` 常常只出 2 行就报错**（"Unable to get system boot time"），你会误判成"守护死了"。

**处理**：改用 `/proc` 交叉验：
```bash
# 进程在不在
ls /proc/<pid>/cmdline && tr '\0' ' ' < /proc/<pid>/cmdline
# 是不是同一个进程（starttime 不变 = 没被换掉）
awk '{print $22}' /proc/<pid>/stat
```

### 5.5 连上了但没横幅
**处理**：别拿「端口在听」当「sshd 活着」。**真验证是读 SSH-2.0 横幅**：
```bash
timeout 5 bash -c 'exec 3<>/dev/tcp/<host>/22; head -c 7 <&3'
# 期望输出：SSH-2.0
```

## 6. 守护起来了，但重启后没了

**症状**：守护当前在跑，重启整机后就没了。

**原因**：**proot 没有 init，没有 systemd，也没有自启机制**。我们自己的机器上也是这样，所以把"拉起来"做成了开工第一步。

**处理**：两条路，按机器选：
- **有 systemd 的机器**（普通 Linux / PC）：装一个 unit，走 `systemctl enable`。
- **proot 机器**（手机 / 平板）：`setsid nohup ... &` 兜底，⛔ 并在文档里明写「**重启后要手工拉**」。

**别装 systemd 单元到 proot 上** —— 那儿没有 systemd，单元文件是死的。

## 7. 聊天室：消息发出去了，但对面看不到

### 7.1 正本在哪
**这一条最要紧**：hub 文件是**唯一正本**，在某台机器上（我们那儿是电脑）。**其他设备只拉不写**。

**为什么**：历史上三台设备各自整份覆盖过对方至少 3 次，把聊天记录搞乱过。

**处理**：投递脚本要认正本所在机器的别名；正本机不可达时，⛔ 不要写本地缓存当正本。

### 7.2 坏行会让整个文件读不出来
**症状**：hub 里有几行坏行，解析器直接崩。

**原因**：并发追加时可能写坏行。我们见过 703 行里 6 行坏（43/63/65/66/67/75）。

**处理**：解析器必须**逐行容错**（跳过坏行、继续读），⛔ 不能一遇坏行就整体失败。跳过的行数要在输出里报出来，让人知道"你可能漏了几条"。

### 7.3 seq 撞号
**症状**：两条消息 seq 一样。

**原因**：多台机器各自生成 seq。

**处理**：撞号集合要**登记在案**（我们有一份 `已知撞号.json`），而不是当作 bug 反复查。

### 7.4 命令行发消息被 shell 吃了
**症状**：长文本发不出去，报 `argument --say: expected one argument`。

**原因**：`--say "长文本"` 会被 shell 吃一层（引号、换行、`$`、反引号）。

**处理**：⛔ 别拼命令行参数。**用 `--say-file <文件>`**，逐字保真。发完**回读一遍**核对内容一致才算发出去。

### 7.5 聊天室插件（GUI 入口）
**现状**：通用包里的是 CLI（`--say` / `--tail` / `--status`）。

**要让别人也能参与**（看得见自己设备发的话、也能回），需要 GUI 入口 —— DSH Web 界面里一个面板，列消息流、能直接回。**这是 v0.2**，v0.1 先把 CLI + 投递跑通。

**给别人用的时候要交代的一句**：CLI 也能参与（`bridge chat --tail 5` 看、`--say-file` 发），只是要会敲命令。

## 8. 脱敏（推公开仓前的最后一道闸）

**⛔ 顺序不能反：先脱敏，再建仓，最后才 push。**

**必须扫掉的**（我们本机真出现过，所以写了闸）：
- Windows 侧工作区前缀（盘符 + 我们的项目根）
- Linux / proot 侧工作区前缀（`/root/` 下的工作目录）
- 内网私有网段（RFC 1918 那三段，带 IP 形状判断，别误伤版本号）
- 三个 agent 的角色名（我们内部用两个字，此处不写出来 —— 写了这份文档自己就带禁词）
- 用户真实姓名 · 真实主机名 / 机型词
- `session` 加短横线前缀的 UUID

⚠️ **写文档时别把禁词当例子抄进来** —— 这份文档自己就踩过一次：把上面几条原样列出来，
结果「讲脱敏的那一节」成了唯一的告警源。**描述它，别复现它。**

**可以留的**：
- `{{WORKSPACE}}` 这类占位符
- `bridge.toml.example` 里的 `example.com` / `localhost`

**判据**：**扫描脚本 exit 0 才算过，不是「我看了一眼没有」。**
脚本必须带**负向测试**：造一个含真路径的假件，扫描必须报红。

## 9. 三台设备各写各的 ≠ 通用包

**这一节提醒做包的人和用包的人**：

我们三台在跑的是**同一个机制的三个独立实现**（不是同一份代码）：
- 手机的收件是 `share_inbox.py`（分拣）+ `watch_share.py`（守护）两个脚本；
- 平板是**一个脚本干三件事**（发现 + 记账 + 通知）；
- 电脑是第三套。

**通用包里的 `receive.py` 只做「按命令归位」**（分格 + md5 判重）—— ⚠️ **不带后台发现层**，不会自己盯着目录，也不会 inotify。要自动，自己在外层挂 watcher（见 §1.1）。
「未读卡片 + 唤起会话」是 DSH 特有上层，⛔ 不进通用包。

**安装脚本只新增不删** ⛔ 不要动对方正在跑的实例。
