# 03 · 故障排查

按**看到的症状**查，不用按模块查。每条给出：症状 → 先看什么 → 常见原因 → 怎么修。

---

## 一、一条命令都不投，也没报错

**先看**：`python -m bridge.post --status`（看「待投 / 被拦 / 积压」三个数）

| 你看到的 | 大概是什么 |
|---|---|
| `发件箱：0 件` | 路径不对。你放件的目录 ≠ `[device.X].outbox` |
| `认得出的 0 件` | 后缀不对：`[post].exts` 默认只有 `.md`，`.MD`/`.txt` 不算 |
| `⛔ 名字不合规 N 件` | 见下面第三节 |
| `待投 N` 但 `--once` 说候选 0 | 台账 `.posted.json` 里已经有同名同 md5 的记录 —— 它是被投过的（改名或改内容再试） |

另外两件容易忘的：

- **`.post.lock` 被占着**：另一个 `--once` 正在跑（或者上一个进程被强杀时文件描述没关干净——
  这在 Linux 上是内核自动回收的，不会真的锁住；在 Windows 上进程一死锁就放）。
  真锁住时的表现是 `--once` 打印「已有一个 --once 在跑，这轮跳过」并 exit 0。
- **计划任务根本没在跑**：`python -m bridge.loop --status` 看「上一轮是什么时候」。

## 二、投了，但对端没有 / 内容不对

```sh
python -m bridge.post --once --dry-run    # 先看清「将投给谁」
```

| 症状 | 原因 |
|---|---|
| 报 `写入失败` | 对端目录不存在或没权限；本包会先 `mkdir -p`，但父目录不可写就没法 |
| 报 `md5 不一致` | 传输被改写（换行符转换、编码转换）。查对端是不是经过了某个会改内容的中间层 |
| 报 `取不到对端 md5（未验成）` | 对端既没有 `md5sum` 也没有 `certutil`。**写入可能是成功的**，只是没证据 |
| 投给了不该收的人 | `[recipients]` 里那个词映射到了多个设备。**这是最贵的一类错**：一次性把信发给所有人 |

> 🔴 「平板和手机」这类话**不能**当收件方用来自动猜设备。
> `[recipients]` 就是那张唯一真话表：写 `"大家" = "*"` 是明确的全投，
> 写错一个词也只是查不到（`bad-target`），不会变成「发给所有人」。

## 三、名字不合规（`bad-act` / `bad-target` / `bad-fields`）

```
⛔ 名字不合规 1 件（这些不会被投）：
   · 通知_给平板_主题_20261107.md
     - bad-act：改一个词：性质只能是 信、回话、同步、知会
```

| 原因 | 改哪 |
|---|---|
| `bad-fields` | 段数/日期/后缀不对，整份改名。格式见 `docs/02_命名与落点.md` |
| `bad-act` | 第一段换成 `[naming].act_kinds` 里的一个 |
| `bad-target` | 第二段换成 `[recipients]` 里有的词 |

两个错会**一起**报出来（先 `bad-target` 后 `bad-act`），别只改一个就以为好了。

老件不想改名：`[naming].enforce_since = "20261105"`（早于这天的按老件放行）。

## 四、同一封信投了两遍

去 `<outbox>/post.log` 按时间对：

| 日志形状 | 原因 |
|---|---|
| 同一秒出现两行同名 | 两个 `--once` 撞在一起了（锁没生效）。查是不是有人绕过本包直接跑了两份，或者计划任务重叠 |
| 间隔几分钟各有一次 | 第 2 次是**内容变了**（md5 变 ⇒ 判成新件）。改文件内容会触发重投，这是设计 |
| 换了名字的两条 | 改了文件名但内容一样、收件方一样 ⇒ 本包判 `same-content` 会拦。若还重投了，说明旧台账里的收件方没覆盖这次的目标 |

> 判重是「读台账 - 判断 - 写台账」，**不是原子的**，所以必须有锁。
> 锁的语义：拿得到 = 没人跑；`AlreadyRunning` = 有人跑（安静跳过，不是错误）。

## 五、聊天室：看不到新消息 / 反复看到旧消息

```sh
python -m bridge.chat --status     # 看「消息条数 / 最大 seq / 游标差几条 / 坏行数」
```

| 症状 | 原因与修法 |
|---|---|
| 「差 N 条」一直不变 | 游标文件写不进去（`<state>/.chat_cursor_<key>` 权限）。它是每台私有的，不是共享的 |
| 明明有新消息，「差 0 条」 | **seq 撞号**：两条消息同一个 seq，按 seq 比就都跳过。新格式游标按行号比，`--status` 里看 `line=` 是不是数字 |
| 归档之后又读了一遍全部 | 游标是老的纯整数格式（没有行号），且落进了已归档区间。执行一次 `--read` 升级成新格式 |
| 报「坏行 N 条」 | 用 `--read` 会把原文记进 `hub.bad.jsonl`（`raw_b64` 解一下就回原文），然后照样跳过 |

手工看一眼游标：

```sh
cat <state>/.chat_cursor_<设备key>
# 7                       ← 老格式
# {"seq": 7, "line": 42}  ← 新格式
```

**别手工把游标往前跳**来「跳过一堆消息」：那是唯一会让你永久丢消息的操作。
要重新读，把游标写成 `{"seq": 0, "line": 0}`（会从归档偏移量之后全读一遍）。

## 六、心跳过期（`.chat.beat`）

```
[X] 心跳：4200s 前（判死线 130s）
```

意思是「守护**活着**但没在干活」——这比进程崩了更难查，因为进程列表里它还在。

按顺序查：

1. `python -m bridge.loop --status` —— 状态 json 里 `last_run_at` 是不是也停了？
2. 状态 json 有、心跳没动 ⇒ 守护没带 `--beat` 跑（心跳不是每轮自动摸的）：
   `python -m bridge.chat --beat` 手工摸一次，看会不会恢复。
3. 时间戳是**未来**的 ⇒ 某台机器的系统时钟不准。心跳算的是 `now - beat`，
   时钟歪了会算出负数或巨大的数。对齐 NTP。
4. `.beat` 文件内容不是数字 ⇒ 有人手写坏了，删掉重摸。

## 七、守护起不来 / 起来了跑一轮就停

| 现象 | 原因 |
|---|---|
| `[X] 已有一个守护在跑（锁被占）` | 真的还有一个。`--status` 会告诉你「在跑」 |
| `[X] 锁文件打不开（...）：PermissionError` | **不是**有人在跑，是环境问题（只读盘/权限/路径被占）。本包故意把这两种情况分开报 |
| 跑一轮就退出、退出码 1 | 那一轮里某台设备连不上。单台的失败**不会**拖垮其它台；看 `post.log` 里哪台失败 |
| 计划任务里一闪就没了 | 计划任务的**工作目录**必须是仓根（`-WorkingDirectory`），否则 `-m bridge.loop` 找不到包 |

Windows 上每次弹黑窗口：那是 `ssh` 作为控制台程序的行为。本包内部调用时加了
`CREATE_NO_WINDOW`；但计划任务里如果 `python` 本身是控制台程序，窗口还是会闪。
要彻底不闪，让计划任务**以「不管用户是否登录」方式运行**（`-User SYSTEM` 或勾选该选项）。

## 八、中文乱码 / 命令直接崩在 print 上

```
UnicodeEncodeError: 'gbk' codec can't encode character ...
```

本包所有入口都会把 stdout/stderr 切到 UTF-8（`enable_utf8_stdio()`），正常情况下不会出现。
如果还出现，说明是**别的**脚本在打印，或者你把本包的输出交给了一个只认 GBK 的管道：

```powershell
$env:PYTHONIOENCODING = "utf-8"     # PowerShell 里临时这么试
chcp 65001                          # 或者把控制台代码页切到 UTF-8
```

文件层面：一律 UTF-8 无 BOM（`bridge.toml` 例外，读的时候兼顾 BOM）。
`.ps1` 必须 UTF-8 **带 BOM**，否则 Windows PowerShell 5.1 会按 ANSI 解，中文全乱。

## 九、收件归位（`bridge.receive`）

| 现象 | 原因 |
|---|---|
| `[X] ... 这一版没有实现` | 你把 `[receive].backend` 写成了 `posix-remote`。它**不是开关**，是要自己实现的接口，见 `bridge/receive.py` 里的 `InboxBackend` |
| 归位了但原件还在 | 默认就不搬（删是不可逆的）。要搬就配 `[receive].processed_dir` |
| 重复的件不再归位 | 正常。台账 `.received.json` 按「文件名 → md5」判重 |
| 同一份内容换个名字又被归位一次 | 归位侧**不做**跨名的内容判重（那是投递侧 `same-content` 的活）。收件侧只认「同一个名字 + 同一个 md5」 |

## 十、自检三连（给别人看也用这个）

```sh
python tests/test_chat.py      # 期望：断言 N/N 通过，退出码 0
python tests/test_post.py      # 期望：断言 N/N 通过，退出码 0
python -m bridge.post --self-test   # 期望：自测 N/N 通过，退出码 0
```

三个都不需要 ssh、不需要真配置 —— 它们在自己的临时目录里造两台假设备。
**跑不通这三个，先别去碰真数据。**

拿到别人报的问题，第一件事也是让他跑这三条并把输出贴回来：
它跑不了 = 环境问题（Python 版本/权限），它跑得了 = 问题在配置或数据上，
两者要查的方向完全不同。

---

> 没有 systemd、`/run/sshd` 缺失导致 sshd 静默退出、`ps -ef` 只出 2 行、inotify 偶漏事件。

## 症状：明明在试跑，信却「投成功」了，而且对端真有那个文件

**先怀疑别名撞车。** `post --once` 只认 `[device.*].aliases` 里的名字，它不知道你想连的是哪台 ——
如果 `~/.ssh/config` 里恰好有个同名 Host 且通，它会**老老实实连过去、把信投到那台真机**，
再跑一遍远端 `md5sum` 对账，于是输出是「投出 1 · verified OK」。

∅ 判据：`post --once --dry-run` 先看「会投给谁」；试跑一律用 `sim-` 前缀的假别名，
或 `transport = "local"` 的单机双目录。**「验证通过」只证明投递成功，不证明投对了地方。**
